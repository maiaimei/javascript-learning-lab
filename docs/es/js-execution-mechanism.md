# JS 执行机制

> 一句话概括：**单线程 + 事件循环（Event Loop）+ 执行上下文栈**

## 1. 核心前提：为什么 JS 是单线程？

- JS 设计初衷是操作 DOM，多线程同时改 DOM 会导致状态混乱
- **同一时间只能做一件事**
- ⚠️ 单线程是 **JS 引擎（V8）** 的特性，不是浏览器。浏览器本身是多线程的（渲染线程、网络线程、定时器线程…）

## 2. 运行时三大件

| 组成部分 | 作用 |
| --- | --- |
| **执行栈（Call Stack）** | 存放正在执行的函数，先进后出 |
| **堆（Heap）** | 存放对象、引用类型数据 |
| **任务队列（Queue）** | 存放异步回调，等栈空了再执行 |

## 3. 同步 / 异步执行示例

```javascript
console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve().then(() => console.log('C'));

console.log('D');

// 输出顺序：A → D → C → B
```

### 执行过程拆解

| 阶段 | 发生了什么 |
| --- | --- |
| ① `console.log('A')` | 同步代码，直接进栈执行 |
| ② `setTimeout` | 交给浏览器定时器线程，0ms 后回调进入 **宏任务队列** |
| ③ `Promise.then` | 微任务，进入 **微任务队列** |
| ④ `console.log('D')` | 同步代码继续执行 |
| ⑤ 同步代码结束，栈空 | **先清空所有微任务** → 打印 `C` |
| ⑥ 微任务清空 | 事件循环取下一个宏任务 → 打印 `B` |

## 4. 宏任务 vs 微任务（重点）

| 类型 | 常见来源 |
| --- | --- |
| **宏任务 (MacroTask)** | `setTimeout` / `setInterval` / `<script>`整体代码 / `I/O` / `UI render` / `setImmediate`(Node) |
| **微任务 (MicroTask)** | `Promise.then/catch/finally` / `queueMicrotask` / `MutationObserver` / `process.nextTick`(Node，优先级最高) |

> 📌 **核心规则**：**每执行完一个宏任务 → 清空所有微任务 → 再取下一个宏任务**
>
> 📌 浏览器每一轮事件循环**最多渲染一次 UI**，渲染发生在宏任务之间。

## 5. 事件循环（Event Loop）完整流程

1. 执行当前宏任务（一开始就是 <script> 整体代码）
2. 遇到同步代码 → 直接执行
3. 遇到异步 → 交给宿主环境（浏览器/Node），时机到了再进队列
4. 当前宏任务结束，执行栈清空
5. 依次执行【所有】微任务（直到队列空）
6. 必要时浏览器重绘
7. 取下一个宏任务，回到 1

## 6. 易踩坑点

```javascript
setTimeout(() => {}, 0)
```

- ❌ 不是 0ms 后立刻执行
- ✅ 0ms 后**有资格进入宏任务队列**
- 真正执行要等：执行栈空 + 微任务清完 + 前面排队的宏任务跑完
- 结论：永远“靠后”

## 7. Node 环境差异（补充）

| 点 | 说明 |
| --- | --- |
| `process.nextTick` | 比 `Promise` 微任务更早执行 |
| Node 11+ | 行为基本和浏览器对齐 |
| 老版本 Node | 阶段模型：`timers → poll → check` |
| 业务开发 | 记住浏览器那套就够用 |

## 8. 速记口诀 🧠

> **同步先跑，异步排队；宏完微清，循环不止。**
